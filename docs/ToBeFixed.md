## 1. Кэш-паттерн «на mouse-move — готовый фон, без перерисовки»: график и стакан ДА, подписи осей НЕТ

**Что проверялось (приказ):** сделано ли в коде так, чтобы график и стакан кэшировались в
видеопамяти и при mouse-move использовались как готовый «фон» без перерисовки всего — включая
подписи осей. **Вывод по коду: для тяжёлых GPU-слоёв — ДА; подписи осей из паттерна ВЫПАДАЮТ.**

### Доказано кодом — кэшируется (на move = блит, не пересборка):

**График (combo / trades)** — кэш в VRAM-текстуре, аналог MoonBot `bm`:
- `chartdx/combo.rs:56-73` — `ComboTex` (`ID3D11Texture2D` в VRAM): запечённая история крестов.
- `chartdx/combo.rs:219` — `need_full = !tex.valid || u_left_px вне margin || смена трансформа`.
  На mouse-move вид не сдвинут → `need_full=false` → ветка блита `chartdx/combo.rs:307-341`
  (`context.Draw(6,0)` с UV-паном — один quad готового битмапа), re-bake НЕ зовётся.

**Стакан (orderbook)** — кэш в VRAM-текстуре, явный аналог MoonBot `bmGlass`:
- `chartdx/orderbook.rs:42-61` — `BookTex` (`ID3D11Texture2D` в VRAM): запечённый фон+бары.
- `chartdx/orderbook.rs:160` — bake ТОЛЬКО `!baked || (dirty && прошло ≥200мс)`; `dirty` ставится
  лишь на смену уровней / Y-трансформа / стиля (`orderbook.rs:147-153`).
- На mouse-move (книга та же, Y та же) → `dirty=false` → bake пропущен → блит готовой текстуры
  (`orderbook.rs:219-247`). Троттл bake ~5 Гц (как MoonBot bmGlass 200мс).

Подтверждается тем, что эти слои гейтятся в prepare по revs, а не по курсору:
`chartdx/mod.rs:583` (orderbook — `book_rev`/`lo`/`hi`), `mod.rs:644-654` (combo — `total`).
Mouse-move не меняет ни один из этих ключей.

### Доказано кодом — НЕ кэшируется (дыра паттерна):

**Подписи осей** — ре-шейпятся (`shape_line`) на КАЖДЫЙ render, в т.ч. на mouse-move, без кэша:
- `axes.rs:52-77` (`label`) и `axes.rs:81-120` (`chip`) — оба зовут `ts.shape_line(...)` каждый вызов.
- `axes.rs:202-220` цикл цен (~8-10 шейпов) + `axes.rs:235-249` цикл времени (7 шейпов).
- `axes.rs:126` `draw` зовётся из `panels/chart.rs:758` (canvas-paint), по КАЖДОЙ панели каждый render.
- `panels/chart.rs:698-704` `on_mouse_move` → `cx.notify()` на смену позиции курсора → render →
  canvas-paint → `axes::draw` → re-shape ВСЕХ подписей шкал.
- Текст подписей шкал на mouse-move НЕ меняется (вид тот же). Легитимно меняются только крестик и
  2 readout-плашки под курсором (`axes.rs:252-309`). Значит ~17 шейпов шкал выброшены зря.
- Эталон для сверки: MoonBot держит `TextWidthInt`-кэш по строке (RENDER_INVALIDATION §4).

**Что замерить:** на mouse-move над чартом в `render_diag.log` подтвердить `combo_bake≈0` и
`orderbook_bake≈0` (кэши не пересобираются — паттерн «фон» работает для GPU-слоёв). Затем
release-профиль стоимости `shape_line` за кадр на mouse-move × число панелей в Tiled-мультичарте —
это и есть цена дыры.

**Открытые вопросы:** почему GPU-слои вынесены в VRAM-кэш с гейтами, а текст осей — нет? Достаточно
ли кэша подписей по ключу (текст, размер, цвет)? Или разнести в render крестик (меняется на move) и
шкалы (не меняются) — звать `axes::draw` для шкал только при смене `AxisSnapshot`, а не на каждый move?

## 2. Метрики CPU/RAM/fps в статус-баре обновляются по приходу данных, а не по часам

**Гипотеза:** нижняя полоска (CPU/RAM/fps) перерисовывается только когда backend будит UI, а тот
будит только при `drain()==true` (пришли данные с фида). Молчит фид (обрыв / неактивный инструмент)
→ цифры машины замирают, хотя в backend они свежие. Класс «обновление сцеплено с данными».

**Точки входа:**
- `main.rs:928` — `b.snap = b.metrics.sample(...)` обновляется в backend безусловно (~96мс).
- `main.rs:952` — `if notify_due && dirty_since_notify { cx.notify() }` — UI будится ТОЛЬКО при `dirty_since_notify`.
- `main.rs:897,920` — `dirty_since_notify |= b.session.drain()` — т.е. «пришли ли данные».
- `main.rs:292-317` — Shell observe → рисует статус-бар; вне backend-notify не зовётся.
- НЕ затронут: conn-статус — он event-driven (`feed/live.rs:298` шлёт `FeedMsg::Status` на разрыв →
  `drain()==true` → бар будится). Проверено: о соединении бар НЕ врёт. Замирает только телеметрия.

**Что замерить:** отключить фид (или дождаться тихого инструмента), смотреть, стоят ли CPU/RAM/fps,
тикает ли при этом conn-статус. Подтвердить, что замирают именно метрики, а не статус.

**Открытые вопросы:** узкий ли это случай (на Binance Futures `subscribe_all_trades` фид почти
никогда не молчит)? Учитывая, что панели теперь cached (top-down не тащит Orders), будить Shell по
своему лёгкому таймеру стало безопасно — или забить как косметику?

## 3. Мелочи (копать в последнюю очередь — реальны, но масштаб микро)

- **present-rate рассинхрон на немратных мониторах.** `panels/chart.rs:433-439` считает
  `effective_present_rate_hz = monitor/round(monitor/60)` (на 144→72), а форк капает continuous к
  жёстким 16667µs (≈60, фактически ~48 из-за vblank-кратности на 144). `ensure_default_window`
  (`moon-chart/view.rs:132`) подбирает phase-clean `px_per_ms` под неверную частоту. На 240/120/60
  совпадает; на 144/165 — фазовая неточность шага скролла (НЕ дрожание, квантизация целопиксельная).
  Копать: видно ли глазом на 144Гц; согласовать частоту chart.rs с фактическим cap форка.
- **Холостой 62.5Гц таймер Main-чарта на паузе.** `panels/chart.rs:182-209` — follow-задача
  просыпается каждые 16мс всегда; при `present_guard.is_none()` (пауза) делает пустой `this.update`.
  1 таймер на группу. Копать: стоит ли парковать задачу при отсутствии guard.
