Live-run status:

- App did not reach chart rendering from plain SSH launch.
- Failure:
  `Error: keyring get: Platform secure storage failure: User interaction is not allowed.`
- Cause: macOS Keychain refuses access to the `moon-terminal` secret from the non-GUI SSH/audit session. This is not a Metal/chartdx failure.
- GUI session did show the expected Keychain prompt:
  `security wants to use your confidential information stored in "moon-terminal" in your keychain.`

Follow-up:

- After allowing the CLI `security` prompt, `security find-generic-password -s moon-terminal -a config-key-v1` succeeds from SSH.
- Direct SSH launch of `moon-gpui` still fails with `User interaction is not allowed`; metadata access for `security` is not enough to grant the app binary access to the secret.
- GUI launch attempts via a shell wrapper and via a real `.app` bundle both start `moon-gpui` as user `m1`, but the process stays alive before any app log is printed.
- `sample` shows the main thread blocked in:
  `SecKeychainFindGenericPassword` -> `SecurityServer::ClientSession::getAcl`.
- Recreating a separate unlocked `moon-test.keychain-db`, signing the real binary, and adding the item with `security add-generic-password -T <moon-gpui>` did not unblock this remote test session.
- Conclusion: clean macOS live-run is blocked by interactive Keychain ACL on this rental machine, not by Metal/chartdx.

## Linux / Ubuntu 24.04 / NVIDIA A40-4Q / DISPLAY=:10

Build status before dependency fix:

- `cargo check -p moon-ui-gpui --bin moon-gpui`: OK.
- `cargo build -p moon-ui-gpui --bin moon-gpui`: OK.
- `cargo build --release -p moon-ui-gpui --bin moon-gpui --features debug-tools`: OK.

Live-run status before dependency fix:

- App did not reach chart rendering with encrypted config generated by a helper process.
- Failure:
  `[INFO moon_core::config::crypto] generated new config encryption key`
  then
  `Error: decrypt failed`

Root cause:

- `keyring` v3 has no default platform credential store features.
- `moon-core` enabled only `windows-native` and `apple-native`.
- On Linux that falls back to `keyring`'s mock store, which is process-local memory.
- Result: one process writes `servers.enc` with one in-memory key; the next process cannot read it and creates another key.
- This is a real Linux dependency bug, not a test-machine issue and not a chart renderer issue.

Fix in working tree:

- `crates/moon-core/Cargo.toml` now enables Linux keyring backend:
  `linux-native-sync-persistent` + `crypto-rust`.
- Local check after fix:
  `cargo check -p moon-core`: OK.
- Linux remote check after fix:
  `cargo check -p moon-ui-gpui --bin moon-gpui`: OK.

Live-run status after dependency fix:

- Release build with `--features debug-tools`: OK.
- Config generation now reaches real Linux secure storage instead of process-local mock.
- New failure on the headless VPS:
  `keyring get: Platform secure storage failure: DBus error: The name org.freedesktop.secrets was not provided by any .service files`
- Meaning: this test machine has no running Secret Service provider (`gnome-keyring`, KWallet Secret Service, or compatible `org.freedesktop.secrets` implementation) in the app session.
- This is a Linux runtime/package prerequisite issue for encrypted config, not chartdx rendering.

Action/next check:

- Install/start a Secret Service provider in the Linux test GUI session, or use a desktop image/session that already has one.
- Rebuild Linux release after committing/pushing the dependency fix.
- Regenerate encrypted config using the real Linux keyring backend in that same GUI/DBus session.
- Rerun live perf with `DISPLAY=:10`, `MOON_RENDER_DIAG=1`, and `MOON_RENDER_DIAG_OPEN_10_BTC=1`.
- Collect `render_diag.log`, process CPU/RAM, and GPU counters only after the app reaches chart rendering.
